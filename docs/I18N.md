# GitVerse — Internationalization & Localization (`i18n`)

> Comprehensive guidelines for bilingual parity, RTL/LTR layout symmetry, translation structure, and automated CI verification.

---

## 1. Supported Locales & Directionality

GitVerse is engineered from the ground up for native bilingual support:

| Locale Code | Language Name | Native Name | Script Direction | Font Family | Dictionary Path |
|---|---|---|---|---|---|
| `en` | English | English | **LTR** (Left-to-Right) | `IBM Plex Sans Variable` | `i18n/locales/en.json` |
| `fa` | Persian | فارسی | **RTL** (Right-to-Left) | `Vazirmatn Variable` | `i18n/locales/fa.json` |

---

## 2. Core Translation Principles

1. **Zero Hardcoded User-Facing Strings**:
   - Every label, placeholder, tooltip, heading, confirmation dialog, badge, and error notice must use the `$t('...')` translation helper.
   - Prohibited:
     ```html
     <!-- FORBIDDEN -->
     <UButton label="Submit Review" />
     ```
   - Required:
     ```html
     <!-- MANDATED -->
     <UButton :label="t('provider.submitReview')" />
     ```

2. **100% Key Parity**:
   - Every translation key present in `en.json` must exist with an equivalent, meaningful translation in `fa.json`.
   - Automated CI verification (`scripts/validate-i18n.mjs`) checks parity on every commit.

3. **Placeholder Consistency**:
   - Variable placeholders (e.g., `{branch}`, `{name}`, `{count}`, `{line}`, `{start}`) must match identically between `en.json` and `fa.json`.

## 3. RTL & LTR Layout Discipline (CSS Logical Properties)

To guarantee automatic, symmetric layout inversion between Persian (RTL) and English (LTR), developers must strictly use CSS logical properties and Tailwind v4 logical utility classes:

### Mapping Table: Physical vs Logical Properties

| Physical (Prohibited) | Logical (Mandatory) | Purpose |
|---|---|---|
| `ml-*`, `mr-*` | `ms-*`, `me-*` | Margin inline start / end |
| `pl-*`, `pr-*` | `ps-*`, `pe-*` | Padding inline start / end |
| `left-*`, `right-*` | `start-*`, `end-*` | Absolute positioning |
| `text-left`, `text-right` | `text-start`, `text-end` | Text alignment |
| `border-l-*`, `border-r-*` | `border-s-*`, `border-e-*` | Border start / end |
| `rounded-l-*`, `rounded-r-*` | `rounded-s-*`, `rounded-e-*` | Border radius start / end |

### Directional Icons & Arrows

Icons that indicate spatial progression (e.g., `i-lucide-arrow-right`, `i-lucide-chevron-right`) must invert in RTL mode:
```html
<UIcon name="i-lucide-arrow-right" class="rtl:rotate-180" />
```

### Technical Values Preservation

Technical entities must always remain Left-to-Right regardless of UI language:
- Git commit hashes (`a1b2c3d`)
- Branch names (`feat/login-flow`)
- File paths (`src/main.rs`)
- Code snippets and diff patches

```html
<span dir="ltr" class="font-mono text-xs">
  {{ pullRequest.source_branch }}
</span>
```

## 4. Automated CI Validation Script

The validation script [`scripts/validate-i18n.mjs`](file:///home/farshid/Desktop/self/gitverse/scripts/validate-i18n.mjs) executes in CI and pre-commit hooks to verify:
- **Key count parity**: Identical key hierarchies across locales.
- **Non-empty values**: No empty string keys in any locale.
- **Placeholder matching**: Matching `{token}` interpolation syntax across translations.

### Run Validation Manually:
```bash
npm run validate:i18n
# or
node scripts/validate-i18n.mjs
```
